# 【SUMO】2車線合流モデルで協調合流を検証する（Step 4・着手前）

## はじめに

前回までに、主線上流2車線、ランプ1車線、600 mの3車線並走区間、下流2車線からなる `highway_merge_v3` を評価した。総需要3,950 veh/h・主線:ランプ=1:2では、5つの乱数seedすべてで需要終了後も車両が残った。今回は、この条件に対して協調合流を検証する。

## 旧モデルの結果を流用しない理由

以前の協調合流は、2流入1流出のpriority junctionで、主線1車線へ速度助言を出す方式だった。v3には2本の主線車線と600 mの並走区間があるため、同じ数値や結論を流用すると道路構造の違いを見落とす。そこで、v3の無制御結果だけを基準に新しいStep 4を始める。

## 比較条件と成功条件

比較条件は総需要3,950 veh/h、主線:ランプ=1:2、seed 7 / 42 / 99 / 123 / 2026、需要投入1,800秒、クリアランス600秒とする。無制御の平均未完了台数は257.6台、平均処理量は3,436.8 veh/hだった。

協調制御は、ランプ側で待機が発生したときだけ、合流端へ数秒で到達する主線車両に緩やかな速度助言を出す。信号、停止線、主線の完全停止は使わない。対象ランプ車両の合流または制限時間で助言を解除し、連続介入を防ぐためのクールダウンを置く。

成功は、平均未完了台数の削減、平均処理量の増加、5 seed中3 seed以上の回復、衝突・テレポートなしの4条件を同時に満たすことと定義する。次回は初期方式の実装と実測結果を示す。

## 初期実装で分かったこと

初期方式を5 seedで実行したところ、協調制御の介入回数は0回だった。未完了台数257.6台、処理量3,436.8 veh/h、回復0/5はいずれも無制御と同じで、衝突とテレポートはなかった。

原因は、ランプ需要の超過が並走区間内の停止ではなく、ランプ上流での流入待ちとして表れたためである。並走区間のランプ車両は停止する前に走行しており、「3秒以上待った車両」という起動条件には該当しなかった。

次の改善では、停止待ち時間を待たず、ランプ専用レーンの終端へ近づいた車両を検知する。主線への助言は引き続き競合車両だけに限定し、同じ5 seedで比較する。

## 改善1も起動しなかった

停止時間の条件を外して再実行しても、介入回数は0回だった。性能も無制御と同一である。終端180 mという観測窓では、ランプ車両と対象主線車両の組が成立していないことが分かった。

次は、600 mの並走区間全体に検知範囲を広げる。ただし主線への助言対象は終端近傍の競合車両1台だけに保つ。観測を上流へ広げても介入を無制限に増やさない設計で、まず制御が実際に働く条件を確認する。

## 改善2で小さな改善、ただし未達

検知範囲を広げると平均139.2回の介入が発生し、未完了台数は257.6台から252.4台、処理量は3,436.8 veh/hから3,447.2 veh/hへ改善した。一方で回復は0/5のままで、成功条件には届かなかった。

ログを見ると、ほぼすべての介入が7秒のタイムアウトで終了していた。ランプ車両が専用レーンを離れても、ネットワークを出るまで助言を解除していなかったためである。次は「専用レーンを離れた時点」を合流完了として解除し、不要な主線減速を減らす。

## 早すぎる解除は悪化した

専用レーンを離れた時点で解除すると、成功解除は平均202.0回になったが、未完了台数は263.0台、処理量は3,426.0 veh/hとなり、無制御より悪化した。下流2車線への収束までを考えると、車線変更直後の解除は早すぎたようだ。

次は7秒保持へ戻し、速度助言を23.5 m/sから20.0 m/sへ強める。ほかの条件を固定して、より大きなギャップが回復につながるかだけを確かめる。

## 強い減速でも回復しなかった

20.0 m/sでは未完了262.0台、処理量3,428.0 veh/h、回復0/5となり、無制御より悪化した。今回の中では23.5 m/s・7秒保持が最良で、未完了252.4台、処理量3,447.2 veh/hだったが、回復は得られていない。

このため、速度だけをさらに調整しても目標達成は期待しにくい。次は、実際の車線変更要求と主線到着を対応づける方式を、別の事前仮説として検証する必要がある。

次の方式では、主線車両を単に早く到着する順で選ばない。ランプ車両と終端到着時刻が最も近く、差が3秒以内の車両だけを助言対象にする。無関係な減速を減らせるかを同じ条件で比較する。

ペアリング型は介入0回だった。ランプを600 m手前から見る一方、主線は260 m手前までしか候補にしておらず、到着時刻を対応づけられなかった。次は主線側も500 m手前・ETA20秒まで観測を広げ、3秒以内の到着ペアだけを維持する。

広域化後は平均2.0回だけ介入したが、未完了266.6台、処理量3,418.8 veh/hで悪化した。レーン1はランプ車両の車線変更先でもあるため、そこを減速させること自体が問題かもしれない。次はレーン1を維持し、レーン2だけへ同じ条件の助言を出す。

## 結論：速度助言だけでは高需要・ランプ偏重を回復できなかった

レーン2へ対象を切り替えた最後の方式も、未完了258.0台、処理量3,436.0 veh/h、回復0/5だった。最良は、並走区間全体を検知し、レーン1へ23.5 m/s・最大7秒の助言を出した方式で、未完了は5.2台減り、処理量は10.4 veh/h増えた。しかし、5 seedすべてで破綻が残った。

このStepで得た結論は、主線の限定的な速度助言は小さな改善傾向を作れても、v3の高需要・ランプ偏重条件を単独では回復できない、というものだ。これは失敗の記録ではなく、次の比較の根拠になる。Step 5では、主線・ランプ双方の負担とTTSでその小さな改善を検証する。Step 6ではRamp Meteringを優先し、ランプ投入量の調整で破綻を防げるか比較する。

よって、「速度助言の有効性と限界を明らかにする」というStep 4の目的は完了とする。
