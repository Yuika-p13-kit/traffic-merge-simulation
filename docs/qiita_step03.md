# 合流の総交通量が同じでも渋滞は変わる？SUMOで主線・ランプの需要比を変えてみた

## はじめに

高速道路の合流容量を考えるとき、まず気になるのは「合流部へ1時間に何台来るか」だ。しかし、総交通量が同じでも、主線とランプのどちらから何台来るかによって流れやすさは変わるのだろうか。

Eclipse SUMOで主線1車線・サブ1車線・合流後1車線の最小モデルを作り、信号などの制御を加えずに需要比だけを変更した。今回の結果では、総需要1,000 veh/hでも、主線:サブが1:2〜1:3では全seedで回復せず、1:4〜1:5では全seedで処理できた。

「合流容量は総交通量だけでは決まらない」という結果を、実験条件とともに整理する。

## モデル

対象は実在JCTの完全再現ではなく、主従関係を持つ合流の最小モデルである。

- 主線: 1車線、優先側
- サブ: 1車線、非優先側
- 合流後: 1車線
- 信号: なし
- Ramp Metering: なし
- シミュレータ: Eclipse SUMO
- 実行・集計: Python

サブ車両は合流可能なギャップを判断して主線へ入る。主線を赤信号で止めたり、合流順序を強制したりはしない。

## 実験設計

総需要を固定し、主線とサブへの配分だけを変更した。

| 項目 | 条件 |
|---|---|
| 総需要 | 800 / 1,000 / 1,200 veh/h |
| 需要比（主線:サブ） | 1:1 / 1:2 / 1:3 / 1:4 / 1:5 |
| seed | 1〜5 |
| 需要投入 | 1,800秒 |
| 回復観測 | 600秒 |

例えば総需要1,000 veh/h・需要比1:4は、主線200 veh/h、サブ800 veh/hに配分する。

状態は次のように分類した。

| 状態 | 判定 |
|---|---|
| `free_flow` | 投入中の停止・挿入待ちがなく、最後に未到着車両もない |
| `queue` | 投入中に待ちが発生するが、600秒以内に解消 |
| `breakdown` | 600秒後にも未到着車両が残る |

## 実行方法

```bash
uv run python experiments/step03_demand_ratio/run.py
```

実行すると、seed別の生データ、条件別の集約CSV、metadataが保存される。

## 結果

### 総需要800 veh/h

全需要比で最終的に全車両を処理できた。ただし、遅延は大きく異なる。

| 需要比 | 平均ピーク待ち台数 | 平均待ち時間 |
|---:|---:|---:|
| 1:1 | 128.8台 | 147.6秒 |
| 1:2 | 144.2台 | 133.4秒 |
| 1:3 | 75.2台 | 79.7秒 |
| 1:4 | 1.2台 | 0.1秒 |
| 1:5 | 1.2台 | 0.2秒 |

容量以下に見える総需要でも、主線車両が多いとサブが利用できるギャップが減り、大きな一時渋滞が発生した。

### 総需要1,000 veh/h

今回もっとも興味深かった領域である。

| 需要比 | 主線 / サブ | queue | breakdown | 平均未到着 | 平均処理量 |
|---:|---:|---:|---:|---:|---:|
| 1:1 | 500 / 500 | 3/5 | 2/5 | 2.0台 | 996.0 veh/h |
| 1:2 | 333 / 667 | 0/5 | 5/5 | 53.2台 | 895.6 veh/h |
| 1:3 | 250 / 750 | 0/5 | 5/5 | 55.0台 | 890.0 veh/h |
| 1:4 | 200 / 800 | 5/5 | 0/5 | 0.0台 | 1,000.0 veh/h |
| 1:5 | 167 / 833 | 5/5 | 0/5 | 0.0台 | 1,002.0 veh/h |

総需要は同じなのに、1:2と1:3では実効処理量が約890〜896 veh/hまで低下した。一方、サブ側の比率がさらに高い1:4と1:5では、全需要を処理できている。

主線は優先側なので、主線車両が一定頻度で到着するとサブ車両が利用できるギャップを細かく分断する。主線需要が十分少なくなると、サブ車両をまとまって処理できる時間帯が生まれる。この相互作用が非単調な結果の一因と考えられる。

### 総需要1,200 veh/h

全需要比・全seedで`breakdown`となった。平均処理量は需要比によって約891〜1,073 veh/hだった。現在のモデルでは総需要1,200 veh/hを無制御のまま処理できない。

## 制御は必要か

全条件に制御が必要なわけではない。800 veh/h・1:4〜1:5では無制御でほぼ問題がなく、制御を加える方が余計な損失を生む可能性もある。

一方、1,000 veh/h・1:2〜1:3は重要な改善対象である。同じ総需要を処理できる需要比が存在するため、物理的な容量不足だけではなく、合流タイミングによる容量低下が含まれている。

次は主線を信号で停止させず、サブ車両が合流待ちになった場合だけ主線車両を緩やかに減速させ、流入ギャップを作る協調合流を試す。

## 注意点

今回の結果には次の限界がある。

- 単純な1車線合流であり、実在道路を再現していない
- 主線・サブ別の待ち時間をまだ集計していない
- `queue`は一時的に1台停止しただけでも成立する
- Total Travel Timeは到着済み車両を対象としている
- 5 seedによる比較であり、破綻確率の精密な推定ではない

特にRamp Meteringのように意図的にサブを待たせる制御では、未到着台数だけを評価すると不公平になる。主線とサブの遅延、全車両のTotal Time Spent、最大待ち時間を分けて評価する必要がある。

## まとめ

SUMOの無制御合流で、総需要と主線・サブの需要比を変えて比較した。

- 800 veh/hは全条件で回復したが、需要比によって待ち時間が大きく異なった
- 1,000 veh/hでは1:2〜1:3が全seedでbreakdownし、1:4〜1:5は全seedで回復した
- 1,200 veh/hは全条件でbreakdownした
- 合流の実効容量は総需要だけでなく、優先側と非優先側への需要配分にも依存した

次の実験では、主線を停止させない協調的なギャップ生成が、1,000 veh/h・1:2〜1:3の容量低下を改善できるか確認する。
