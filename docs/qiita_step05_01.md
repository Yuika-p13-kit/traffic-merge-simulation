# 平均旅行時間だけでは渋滞を見落とす——SUMO合流実験にTTSと流入別指標を追加した

## はじめに

これまで、主線1車線・サブ1車線・合流後1車線の単純なSUMOモデルで、無制御合流と主線車両への速度助言を比較してきた。

限定的な速度助言を行うStep 4-2では、総需要1,000 veh/h・主線:サブ=1:3で、処理量と未到着台数に改善傾向が見えた。しかし、全車両の平均値だけでは「主線の小さな損失と引き換えにサブだけを改善していないか」「終了時に残った車両を無視していないか」が分からない。

そこでStep 5-1では、主線とサブを分けて評価し、シミュレーション終了時にネットワーク内へ残る車両も含めたTotal Time Spent（TTS）を追加した。需要条件も15種類へ拡張したところ、協調制御が有効そうな領域は非常に限定され、逆に大きく悪化する条件も見つかった。

## なぜ平均旅行時間だけでは不十分か

SUMOのtripinfoは、目的地へ到着した車両について旅行時間や待ち時間を出力する。終了時に渋滞へ残った車両はtripinfoへ現れない。

混雑が強い戦略ほど未到着車両が増える場合、到着車両だけの平均旅行時間は性能を良く見せる可能性がある。そこで、各シミュレーションステップでネットワーク内にいる全車両へ1秒ずつ加算した。

```text
TTS = Σ（各ステップのネットワーク内車両数 × ステップ長）
```

この方法なら、途中で到着した車両は滞在していた時間だけ、終了時に残った車両は終了時刻まで評価される。

## 追加した指標

- 主線・サブ別の平均待ち時間と総待ち時間
- 主線・サブ別のピーク待ち行列
- 主線・サブ別の到着・未到着台数
- ネットワーク全体と流入別のTTS
- 介入開始後30秒以内に合流したサブ車両数
- 従来の状態分類、処理量、未到着台数

制御パラメータはStep 4-2から変更していない。評価指標と需要範囲だけを拡張し、結果を見ながら制御条件まで変えることを避けた。

## 実験条件

| 項目 | 条件 |
|---|---|
| 総需要 | 800 / 1,000 / 1,200 veh/h |
| 主線:サブ | 1:1〜1:5 |
| 戦略 | 無制御 / 限定協調制御 |
| seed | 1〜5 |
| 需要投入 | 1,800秒 |
| クリアランス | 600秒 |
| 合計 | 150ラン |

## 結果

協調制御による無制御比の変化を抜粋する。

| 条件 | TTS | サブ平均待ち | 処理量 | 未到着 |
|---:|---:|---:|---:|---:|
| 800・1:2 | -0.5% | -0.5秒 | ±0.0 veh/h | ±0.0台 |
| 800・1:3 | +15.8% | +49.5秒 | ±0.0 veh/h | ±0.0台 |
| 1,000・1:3 | -0.2% | -5.4秒 | +15.2 veh/h | -7.6台 |
| 1,000・1:4 | +6.1% | +35.4秒 | -77.2 veh/h | +38.6台 |
| 1,200・1:5 | +1.6% | +47.5秒 | -114.0 veh/h | +57.0台 |

### 改善候補は1,000 veh/h・1:3

この条件では、TTSが0.2%、サブ平均待ち時間が5.4秒、未到着台数が7.6台改善した。処理量も15.2 veh/h増えた。

ただし、TTSが改善したのは5 seed中3 seedで、差も小さい。Step 4-2で見えた改善傾向は残ったが、安定した優位性を確認したとはいえない。

### 需要領域を広げると悪化条件が見つかった

800 veh/h・1:3ではTTSが15.8%増加した。1,000 veh/h・1:4では処理量が77.2 veh/h減り、未到着が38.6台増えた。1,200 veh/h・1:5では処理量が114.0 veh/h減った。

状態分類を見ると、無制御のbreakdownをqueueへ改善したランは0だった。一方、queueからbreakdownへ悪化したランは6あり、5ランが1,000 veh/h・1:4だった。

単一パラメータの協調制御を全需要条件へ適用する方法は不適切である。

## 介入の大半はタイムアウトした

対象サブ車両が8秒以内に合流した成功率は、最も高い条件でも約9.1%だった。改善候補の1,000 veh/h・1:3でも約7.0%である。

30秒の観測窓では複数のサブ車両が合流している。しかし、それが速度助言で作ったギャップを利用したのか、自然に合流したのかは区別できない。「介入後に合流した」という相関と、「介入によって合流できた」という因果は分けて扱う必要がある。

## 主線の待ち時間が0秒だった理由

主線平均待ち時間は全条件で0秒だった。これは主線への影響がゼロという意味ではない。

SUMOの待ち時間は、速度が0.1 m/s未満になった時間を数える。今回の速度助言は主線を22.5 m/sへ減速させるが停止させないため、待ち時間には現れない。主線の損失には、自由走行時との差や主線TTSを使う必要がある。

## TTSにも残った見落とし

結果を検証すると、SUMOがロードした車両数と、TraCIで実際の出発を確認した車両数が69ランで一致しなかった。

高需要時には、出発予定時刻になっても流入エッジへ挿入できず、ネットワークの外で待つ車両が発生する。Step 5-1のTTSはネットワーク内の未到着車両を含むが、この挿入待ち時間を含まない。

特に1,200 veh/hでは条件平均で約90〜109台が挿入待ちになる場合があり、混雑損失を過小評価している。評価指標を追加したことで、さらにその指標自身の欠落が見つかった。

## 次のステップ

Step 5-2では、予定出発時刻から実際に道路へ入る時刻までの挿入待ち時間をTTSへ追加する。

```text
完全版TTS = ネットワーク内滞在時間 + 挿入待ち時間
```

この定義を固定してから、1,000 veh/h・1:3のパラメータ感度と、サブ側だけを制御するRamp Meteringを比較する。

## まとめ

- 主線・サブ別指標とネットワーク内TTSを追加した
- 1,000 veh/h・1:3だけが協調制御の改善候補だった
- breakdownを解消したランはなく、悪化したランが6あった
- 介入の大半はタイムアウトし、効果の因果判定も未完成だった
- TTSが挿入待ち車両を含まない問題を発見した
- Step 5-2で挿入待ちを含むTTSへ修正する

平均値を増やすだけでは、公平な評価にはならない。どの車両が集計から外れているかまで確認して、初めて渋滞戦略を比較できる。
