# SUMOで高速道路合流の「流せる限界」を探す——終了時刻の罠と、5 seedで見えた破綻境界

## はじめに

高速道路の合流制御を比較する前に、まず無制御の合流がどの程度の交通需要まで処理できるのかを把握したい。

本プロジェクトでは、Eclipse SUMOを使って主線1車線・従線1車線・合流後1車線の単純な合流モデルを構築している。Step 2では主線需要を固定し、従線需要を段階的に増やすことで、待ち行列が発生しても解消できる状態と、需要投入後も車両が残る状態の境界を調べた。

今回の主な結果は次のとおりである。

- 主線200 veh/h、従線0 veh/hでは `free_flow`
- 従線50〜818 veh/hでは、調査した条件の多数決で `queue`
- 従線819 veh/hで初めて5 seed中4件が `breakdown`
- 今回の判定条件における最初の多数決破綻点は、総需要1,019 veh/h

ただし、1,019 veh/hは道路一般に通用する容量値ではない。今回のネットワーク、車両モデル、需要投入時間、乱数seed、および「投入終了後600秒以内に解消するか」という判定を組み合わせた、実験上の境界である。

## 実験の目的

次に総需要を固定して主線・サブの需要比を比較する。その前段階として、次の3状態を再現可能な基準で区別することを目的とした。

| 状態 | 判定 |
|---|---|
| `free_flow` | 需要投入中にSUMO上の停止・挿入待ちがなく、クリアランス後の未到着車両もない |
| `queue` | 需要投入中に停止・挿入待ちが生じるが、クリアランス中にすべて解消する |
| `breakdown` | クリアランス終了後も1台以上の未到着車両が残る |

ここでいう `queue` は「何も問題がない状態」ではない。投入中には待ち行列が発生しているものの、追加需要を止めれば所定時間内に回復できた状態である。一方の `breakdown` は、需要投入を止めた後も今回設けた回復時間内には処理しきれなかった状態を表す。

## シミュレーションモデル

対象は、実道路を忠実に再現したものではなく、合流問題の構造を調べるための最小モデルである。

- 主線: 1車線
- 従線: 1車線
- 合流後: 1車線
- 信号・ランプメータリング: なし
- 合流制御: なし
- シミュレータ: Eclipse SUMO
- 実行・集計: Python

主線は200 veh/hに固定し、従線を0〜1,000 veh/hまで増やした。粗い探索では50 veh/h刻み、境界付近では1〜5 veh/h刻みで追加計測した。

## 実験条件

| 項目 | 設定 |
|---|---:|
| 主線需要 | 200 veh/h |
| 従線需要 | 0〜1,000 veh/h |
| 需要投入時間 | 1,800秒 |
| クリアランス時間 | 600秒 |
| シミュレーション終了 | 2,400秒 |
| seed | 1, 2, 3, 4, 5 |
| 状態の集約 | seed間の多数決 |
| 同数時の扱い | より重い状態を採用 |

各交通量条件につき5回実行した。たとえば `queue` が3回、`breakdown` が2回なら、その条件の代表判定は `queue` とする。

## 終了時刻と需要投入時刻を分ける

今回、特に重要だったのがクリアランス時間である。

需要を1,800秒まで投入し、同じ1,800秒でシミュレーションも終了すると、終了直前に正常に流入した車両は、単に走行を終える時間がなかっただけでも「未到着」になる。この値をそのまま使うと、正常な交通流まで破綻と誤判定してしまう。

そこで、需要投入は1,800秒で止めたうえで、シミュレーションだけを2,400秒まで継続した。

```text
0秒                    1,800秒                 2,400秒
|------ 需要を投入 ------|------ 回復を観測 ------|
                         <--- 600秒 --->
```

判定には次の考え方を用いた。

```python
def classify_state(unfinished_vehicles: int, peak_queue_vehicles: int) -> str:
    if unfinished_vehicles > 0:
        return "breakdown"
    if peak_queue_vehicles > 0:
        return "queue"
    return "free_flow"
```

`peak_queue_vehicles` は需要投入中のSUMO summaryから取得し、未到着台数はクリアランス終了時点で読み取る。この分離により、「途中で詰まったが回復したケース」と「回復時間を与えても車両が残ったケース」を区別できる。

## 実行方法

前提はPython 3.13以上、uv、Eclipse SUMOである。プロジェクトのルートで次を実行する。

```bash
uv sync

export SUMO_HOME="/Library/Frameworks/EclipseSUMO.framework/Versions/Current/EclipseSUMO"
export PATH="$SUMO_HOME/bin:$PATH"

uv run python experiments/step02_throughput/run.py
```

実行後、次の3ファイルが生成される。

- `experiments/step02_throughput/results/throughput_raw.csv`: seedごとの生データ
- `experiments/step02_throughput/results/throughput_summary.csv`: 交通量条件ごとの集約結果
- `experiments/step02_throughput/results/metadata.json`: seed、時間、探索範囲、判定定義

探索条件を変更する場合は引数で指定できる。

```bash
uv run python experiments/step02_throughput/run.py \
  --main-rates 200 \
  --side-rates 800,805,810,815,816,817,818,819,820,840 \
  --duration 1800 \
  --clearance-time 600 \
  --seeds 1,2,3,4,5
```

## 結果

全体の状態遷移は次のようになった。

| 主線 (veh/h) | 従線 (veh/h) | 集約判定 |
|---:|---:|---|
| 200 | 0 | `free_flow` |
| 200 | 50〜818 | `queue` |
| 200 | 819〜1,000 | `breakdown` |

従線50 veh/hの時点ですでに需要投入中の待ち行列は観測された。ただし、従線818 veh/hまでは、5 seedの多数でクリアランス中に解消した。

境界付近を詳しく見ると、1 veh/hの違いで多数決の結果が切り替わった。

| 主線 (veh/h) | 従線 (veh/h) | queue | breakdown | 平均ピーク待ち台数 | 平均待ち時間 (秒) | 平均未到着台数 | 判定 |
|---:|---:|---:|---:|---:|---:|---:|---|
| 200 | 818 | 3/5 | 2/5 | 179.4 | 70.88 | 1.4 | `queue` |
| 200 | 819 | 1/5 | 4/5 | 187.4 | 73.87 | 2.4 | `breakdown` |
| 200 | 820 | 1/5 | 4/5 | 191.8 | 76.29 | 9.8 | `breakdown` |

従線819 veh/hでは、seed 2だけがクリアランス内に全車両を処理し、残る4 seedでは1〜5台が未到着となった。従線820 veh/hでも1 seedは `queue` に留まったが、残る4 seedでは6〜20台が未到着だった。

したがって、今回の条件での最初の多数決破綻点は次の値になる。

```text
主線需要 200 veh/h + 従線需要 819 veh/h = 総需要 1,019 veh/h
```

## 結果から分かること

### 1. 破綻は単一の決定的な点ではなく、確率的な遷移として現れる

818 veh/hでは2 seed、819 veh/hでは4 seedが `breakdown` になった。境界付近では同じ需要条件でも結果が揺らぐ。したがって「819なら必ず破綻し、818なら必ず回復する」とは言えない。

今回の819 veh/hは、5 seedによる多数決の分類が初めて切り替わった点である。より厳密に扱うなら、seed数を増やし、需要条件ごとの破綻確率や信頼区間を示すべきである。

### 2. 平均未到着台数だけでは状態を表しきれない

818 veh/hの平均未到着台数は1.4台だが、これは全seedで少しずつ残ったという意味ではない。3 seedは0台まで解消し、2 seedで1台と6台が残った結果である。

平均値に加え、`queue 3/5`、`breakdown 2/5`のようにseed別の発生回数を併記することで、境界の不安定さが分かりやすくなる。

### 3. 「容量」は判定時間に依存する

本実験の `breakdown` は、追加需要を止めてから600秒後にも未到着車両が残ることを意味する。クリアランスを300秒にすれば破綻判定は増え、1,200秒にすれば減る可能性がある。

したがって、今回得たのは物理的・普遍的な道路容量ではなく、「600秒以内に回復すること」を条件とした運用上の境界である。

### 4. 待ち行列の発生と、処理不能は別の現象である

従線50〜800 veh/hではすべてのseedが `queue` だった。つまり、投入中に一時的な待ち行列が生じても、需要停止後には処理できている。

合流制御を評価するときは、待ち行列を一度でも発生させたかだけでなく、ピーク長、待ち時間、回復時間、未処理車両を分けて見る必要がある。

## この実験の限界

今回の結果を解釈するうえで、少なくとも次の制約がある。

- 主線需要は200 veh/hの1条件のみ
- seedは5個のみ
- 需要投入は1,800秒、クリアランスは600秒に固定
- 単純な1車線合流モデルであり、実在JCTの道路形状や交通需要を再現していない
- 車種構成、運転者特性、合流挙動のパラメータ感度を調べていない
- `breakdown` は未到着車両が1台以上という厳しい二値判定

このため、「この道路の容量は1,019 veh/h」と一般化することはできない。今回の価値は、後続の制御比較に使える再現可能な境界条件を得た点にある。

## 次のステップ

次は、信号などの制御を追加せず、総需要を固定して主線・サブの需要比を比較する。

- `free_flow`: 主線200、従線0 veh/h
- `queue`: 主線200、従線800〜818 veh/h付近
- `breakdown`: 主線200、従線819〜900 veh/h付近

需要比（主線:サブ）を1:1〜1:5で変え、同じ総需要でも実効容量や待ち時間が変わるかを同じseed・時間・評価列で確認する。

その結果から追加制御が必要な条件を選び、まずは主線を停止させない協調的なギャップ生成を比較する。

## まとめ

SUMOの単純な無制御合流モデルで、主線200 veh/hに対する従線需要の破綻境界を探索した。

- 需要投入終了後に600秒のクリアランスを設け、終了直前の正常走行車両を破綻と数える問題を避けた
- 5 seedを多数決で集約し、単発実行への依存を減らした
- 従線818 veh/hは `queue` 3/5、`breakdown` 2/5
- 従線819 veh/hは `queue` 1/5、`breakdown` 4/5
- 今回の判定条件では、総需要1,019 veh/hが最初の多数決破綻点となった

境界付近では乱数seedによる揺らぎが大きい。容量を一本の線として断定するより、条件付きの破綻確率として扱う必要があることも見えてきた。

今回得た境界を、次の需要比比較と協調合流比較のベースラインとして利用する。
